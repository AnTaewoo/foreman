## 1. 한 줄 정의 (코드가 실제로 하는 것)

로컬 경로의 저장소 + Goal 문장을 넣으면, LLM이 Plan을 쓰고 → 사람이 GitHub 코멘트 `/approve`로 승인하면 → LLM이 Task 그래프로 분해해 Issue(dry-run)를 만들고 → Scheduler가 의존성·경로 겹침을 풀어 Task를 배정하고 → 격리된 Coding Agent가 브랜치에서 코드를 고쳐 테스트를 통과시키고 PR(dry-run)을 연다. 모든 상태 변화는 **서명된 append-only 이벤트**로만 기록된다.

## 2. 런타임 토폴로지

- API 프로세스(uvicorn `control_plane.api.app:app`): FastAPI 라우터, IdempotencyMiddleware(프로세스 메모리), GoalRunner(in-process, LangGraph, thread_id=goal_id; Postgres면 AsyncPostgresSaver, sqlite면 MemorySaver; interrupt 대기 목록 `_waiting`은 프로세스 메모리).
- Postgres 16(events/tool_calls/8 엔티티) + Redis 7 Streams `events:{project_id}`(+`:retry`).
- OutboxRelay / Projection(consumer group) / Scheduler(consumer group, ingest) — **한 프로세스로 묶어 상주시키는 엔트리포인트가 없다.** 스크립트(`e2e_dry_run.py`, `pc4_run_tasks.py`, `pc1_roundtrip.py`)와 테스트 conftest에서만 조립.
- 워커 컨테이너 `foreman-worker:dev`(`python -m worker <task_id>`): `WORKER_*` env만, secrets 없음, GitHub는 항상 Dry. `DockerCliLauncher`는 정의만 있고 호출자 없음.
- MinIO: 선언만, 사용처 없음.

## 17. 구조적 특징과 리스크

1. 단일 진실 = 이벤트 체인. DB 엔티티는 projection 결과. `verify_chain_db`로 재검산.
2. 워커는 신뢰하지 않는다(DB·secrets·토큰 없음, 미서명 이벤트를 Scheduler가 서명).
3. 읽기-쓰기 일관성 지연(API 202 → relay → projection). Scheduler는 메모리 memo로 read-your-writes.
4. 프로세스 메모리의 운영 상태: `GoalRunner._waiting`, `IdempotencyMiddleware._store`, `DeliveryCache`, Scheduler `in_flight`. API 재시작 시 승인 대기 Goal이 `/approve` no-op. 다중 프로세스 불가.
5. 상주 컴포넌트 조립 부재.
6. Plan 승인은 GitHub 코멘트로만. 인증은 헤더 문자열뿐.
7. Task 완료 ≠ 병합. Dry 모드에서는 `pr.merged`가 없어 의존 Task가 멈춘다.
8. 작은 모델 대응 흔적(느슨한 파서, `min_tasks`, 프롬프트 근거 주석 등).
