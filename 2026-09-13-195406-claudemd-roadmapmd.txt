  Foreman — 코드 기준 아키텍처 (as-built)

  ▎ 작성 근거: 소스와 pyproject.toml, Makefile, docker-compose.yml,

  1. 한 줄 정의 (코드가 실제로 하는 것)

  로컬 경로의 저장소 + Goal 문장을 넣으면, LLM이 Plan을 쓰고 → 사람이 GitHub
  코멘트 /approve로 승인하면 → LLM이 Task 그래프로 분해해 Issue(dry-run)를
  만들고 → Scheduler가 의존성·경로 겹침을 풀어 Task를 배정하고 → 격리된 Coding
  Agent가 브랜치에서 코드를 고쳐 테스트를 통과시키고 PR(dry-run)을 연다. 모든
  상태 변화는 서명된 append-only 이벤트로만 기록된다.

  4. 데이터 모델

  - 엔티티 8 + 1: projects goals epics tasks runs decisions agents events 
    tool_calls. ID는 ULID, 시간은 UTCDateTime.
  - events: PK는 append 순번 seq, ULID id는 unique. canonical_json 텍스트가 서명
    대상, payload JSONB는 조회용 사본. 부기 컬럼 4개만 UPDATE 가능(Postgres
    트리거가 본문 UPDATE/DELETE 거부).
  - tool_calls: run.tool_called만 따로 저장. 서명 없음, 인자는 digest만.
  - tasks: depends_on·blocks(역방향)·owned_paths·attempt_count/max_attempts(3)·p
    r_merged_at.
  - runs: outcome + agent_outcome 병기, tool_call_count는 재계산, denied_count.
  - decisions·agents: 테이블만 있고 쓰는 코드 없음.

  5. 이벤트 소싱 코어

  - 봉투: Event(id, project_id, ts, actor, type, subject, payload, 
    correlation_id, causation_id, signature). payload는 JSON 원시형만.
    correlation_id는 goal_id 또는 project_id. signature는 발행자가 채우면 오류,
    저장 시점에 sign(prev, canonical).
  - 타입 44개: goal 6 · epic 3 · task 9 · run 5 · decision 5 · pr 6 ·
    policy/budget 4 · project/agent/control 6. 전부 핸들러 등록, MVP 1 미사용은
    noop.
  - 흐름: append_signed(project별 advisory lock) → OutboxRelay
    XADD(at-least-once) → consumer group(XAUTOCLAIM 30s) → Projection.apply.
    InvalidTransition/OrderingError는 :retry 스트림에 5→30→300→1800→7200초 지연,
    5회 후 projection_error. 워커 발 미서명 이벤트는 Scheduler.ingest가 서명해
    넣는다.
  - 조회: GET /events?since=<seq>, WS /stream?since=(replay + live, id로
    dedupe), verify_chain_db.

  6. 상태 머신

  - Task: draft→ready(issue 있으면 즉시) → assigned→running →
    in_review(task.completed) → done(pr.merged). 실패는 attempt<max면 ready,
    아니면 blocked. running→awaiting_decision, blocked→ready(task.retried)
    전이는 있으나 발행자 없음.
  - Goal: draft→planning→awaiting_plan_approval→active→done, active↔blocked.
    Epic: pending→active→done. Decision: 표만 있고 코드 없음.

  17. 구조적 특징과 리스크

  1. 단일 진실은 이벤트 체인. DB는 projection 결과일 뿐이고 verify_chain_db로
     재검산 가능.
  2. 워커는 신뢰하지 않는다. DB·secrets·토큰 없음, 거부도 감사 이벤트로 남는다.
  3. 읽기 지연: API는 202 후 relay→projection을 거쳐야 조회에 보인다.
     Scheduler는 메모리 memo로 read-your-writes.
  4. 프로세스 메모리 상태: GoalRunner._waiting, Idempotency 저장소, delivery
     캐시, in_flight. API 재시작 시 승인 대기 Goal은 체크포인트에 남지만
     _waiting이 비어 /approve가 no-op. 다중 프로세스 불가.
  5. 상주 컴포넌트 조립 부재. 현재 플랫폼은 API 프로세스 + 스크립트 조합이다.
  6. Plan 승인은 GitHub 코멘트로만. API 승인 엔드포인트 없음.
  7. Task 완료 ≠ 병합. done은 pr.merged 웹훅이 와야 하고, Dry 모드에서는 e2e
     스크립트가 직접 pr.merged를 발행해 진행시킨다. 의존 Task는 선행이
     done이어야 배정된다.
  8. 작은 모델 대응 흔적(느슨한 파서, extract_json, min_tasks, 근거 주석)이
     코드에 남아 있다.
